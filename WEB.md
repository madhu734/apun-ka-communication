# Web client

The deployed client lives in `web/` and runs at [chat.tmadhu.me](https://chat.tmadhu.me). Use the [deployment notes](README.md) for changes, and the [API contract](API.md) for server routes. The remainder of this file preserves the original feature brief for future revisions.

Build the Mandy Chat web client for `https://chat.tmadhu.me` using React, TypeScript, Vite, the official PocketBase JS and LiveKit JS SDKs, and a service worker. Implement the accompanying API.md exactly. Add a local development proxy for PocketBase requests and use the deployed origin in production. Provision test sign-ins outside source files and never expose backend, LiveKit or Firebase server secrets. Use browser storage only for the minimum session data, with strict CSP, escaped text rendering and no third-party scripts.

Build a responsive private chat with email/password sign-in, paired conversations, newest 30 messages, older-page scroll anchoring, replies, edits for the sender, reactions, read status, presence and typing. Queue failed sends with stable client IDs and reconcile pending items on reconnect. Lazy-load thumbnails and fetch protected media on demand, including recorded voice notes. Handle session expiry and explicitly clear local state on logout. Cache the app shell only and avoid caching private API responses in the service worker.

Use one persistent call controller per app session. Ring from PocketBase state while open, and register Web Push when the user enables notifications. Display an incoming audio or video call with accept, reject and timeout. Use a stable installation ID. On accept, fetch the call token and connect. Show calling, reconnecting and ended states. Toggle mic, camera and front/rear camera without rebuilding the room. Overlay a compact chat composer and recent messages over video. Send through the same messages API with in_call=true. Minimize the call to a corner within the app and adapt subscription quality to rendered size. Add screen share when browser support and user permission allow it. Capture tab audio only when the browser provides it.

Use Opus, prefer H.264 where the SDK and device support it, and keep VP8 as the fallback. Offer Auto up to 720p/30, Smooth at 360p/15, and Audio-only. Downgrade video before sacrificing audio. Follow SDK permission and reconnect events. Gracefully handle denied media permissions, busy calls, concurrent accept, missing devices, expired notifications and a missing camera.

Use the SDK's congestion control and adaptive subscriptions. Keep a single preferred video codec per publisher and avoid simultaneous fallback encoding unless a device compatibility test requires it. On a sustained poor connection lower camera quality one step. Offer Audio-only if audio still breaks up. Restore a higher video tier only after the connection has been stable for at least 15 seconds. In the minimized view request the lowest useful layer. Keep mic echo cancellation and noise suppression enabled where supported. Pause background thumbnails, uploads, and large downloads during a degraded call.

Treat SDK reconnection as the same call. Keep the conversation and controls in place, show a small reconnecting state, and retry room join with a fresh token only if the SDK cannot resume. On recovery, recheck the call record before restoring tracks. Log local aggregate call setup time, selected transport, reconnect duration, RTT, jitter and loss for QA. Avoid logging tokens or media. Check audio intelligibility and recovery when switching Wi-Fi to mobile data and when video competes with a file upload.

Verify with two separate signed-in accounts on different profiles and at least one phone browser. Test a dropped connection with pending messages, protected attachment revocation, live in-call chat, mic and camera toggles, screen share, notification display and deduplication. Leave browser background calling as best effort and guide mobile users to Android for persistent calling.
